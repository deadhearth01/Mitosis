# Windows release readiness (Stage 17)

Status: **release candidate pipeline exists and is reproducible; the app is not
release-ready** — the clone engine is unimplemented (Stage 6+ framework only,
catalog empty) and no clean-machine run has been performed. Every claim below is
tied to build evidence from this stage; untested items are marked.

Deliberately **not** changed this stage (no evidence justifying it, and each
would be a real architecture decision for a later stage): MSIX packaging,
self-contained .NET, ARM64, a different minimum OS.

## Runtime prerequisites

A machine outside a .NET development environment needs both, x64:

1. **.NET runtime 10.0** — the runtime config declares `Microsoft.NETCore.App`
   10.0.0. The normal ".NET Desktop Runtime 10 (x64)" installer satisfies it.
2. **Windows App SDK runtime ≥ 2.5** — `Bootstrap.cs` initializes the dynamic
   dependency with minimum version 2.5. Without it the app cannot start.

The app ships `Microsoft.WindowsAppRuntime.Bootstrap.dll` inside its own folder
(present in the publish output, verified), but the *machine runtime* is still
required for unpackaged apps.

### What the user sees when a prerequisite is missing (Stage 17 change)

Before this stage, `Bootstrap.Initialize()` threw inside `Main`, so the .NET
unhandled-exception dialog showed a stack trace (which leaks local install
paths). Now a `PrerequisiteException` is caught in `Program.Main` and shown as
a Win32 `MessageBox` error dialog whose text names the missing component and
the HRESULT — generated by the unit-tested
`StartupDiagnostics.DescribeMissingAppSdk` (no filesystem, no network, no
paths), then the process exits with code **101**. All other exceptions still
surface normally. The dialog behavior itself is a pending manual check (no
desktop session verified in this stage).

## Build and publish

```powershell
cd windows
dotnet restore Mitosis.sln
dotnet build Mitosis.sln -c Release --no-restore
dotnet test --solution Mitosis.sln -c Release --no-build

# Release candidate: publish + content sanity checks + SHA-named zip
powershell -ExecutionPolicy Bypass -File scripts\publish-release.ps1
```

The script pins the exact recipe (Release, `win-x64`, `--self-contained false`)
and refuses to produce a zip unless it contains the exe, the App SDK bootstrap
DLL, `deps.json`/`runtimeconfig.json`, all 13 brand pose assets, and no
source/tooling/user-data files. It is the same command CI runs.

Archive note: `Compress-Archive` writes backslash-separated entry names.
That is Explorer- and CI-friendly (the artifact is consumed on Windows only),
but would extract oddly under non-Windows tools.

## CI (`.github/workflows/windows-ci.yml`)

- `build-test` (existing, unchanged): restore, Release build, full suite, TRX.
- `publish-release-candidate` (Stage 17): runs after tests pass on the same
  `windows-latest` image, runs `scripts/publish-release.ps1`, and uploads
  `windows-release-candidate` = `Mitosis-windows-x64-<sha>.zip` (14-day
  retention). Nothing is published externally, signed, or attached to a release
  page; the macOS `release.yml` workflow is untouched.

## Release checklist (current truth)

Before anything could be called 1.0 for Windows:

- [ ] Merge `WindowsVersion` after all stages; CI green including the
      `windows-release-candidate` artifact (automated; working).
- [ ] Decide and stamp a real `FileVersion`/`ProductVersion` (currently
      `1.0.0.0` placeholder — `ProductVersion` at least carries the commit).
- [ ] App icon: the exe has no `.ico` (csproj has no `ApplicationIcon`; the
      macOS branding in `Assets/` must not be modified — drawing a Windows icon
      is an outstanding design decision).
- [ ] Code signing: none. Windows SmartScreen blocks unsigned exes; decide
      Authenticode strategy before any public distribution.
- [ ] Clean-machine runs of the published zip with .NET 10 runtime + App SDK
      2.5 runtime, and with both missing (dialog + exit code 101 path) —
      **pending, not testable in this environment**. The only desktop session
      ever used was this dev machine (Windows 11 25H2; last full app launch
      verified in Stage 2, `docs/WINDOWS-DISCOVERY.md`).
- [ ] Windows 10 1809+/**Windows 11 24H2/23H2** compatibility runs — untested;
      only Windows 11 25H2 is verified.
- [ ] ARM64 — out of scope (`Platforms=x64`).
- [ ] Installer (MSIX, winget manifest, or zip-only) — undecided; unpackaged
      zip + manual runtime prerequisites is the current model.
- [ ] **The clone engine itself** — the product's core (clone, launch, refresh,
      delete, recovery) is framework-only with an empty strategy catalog and
      closed execution gates; UI actions show honest "not available in preview"
      dialogs. This is the largest real blocker and out of Stage 17's scope.
